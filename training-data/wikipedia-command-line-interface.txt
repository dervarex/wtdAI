A command line interface CLI also known as a command line shell is a means of interacting with software via commands each formatted as a line of text. The concept of interacting with a computer via text evolved over two decades transitioning from hardware to sophisticated software. Before the CLI computers were programmed using physical switches or punched cards. The shift toward a command style interaction began with the use of teleprinters or teletypes. Early systems such as the Whirlwind I at the Massachusetts Institute of Technology MIT began using typewriter like inputs to give users direct control departing from batch processing in which a user submitted a stack of cards to an operator and received the results hours later. Devices such as the Teletype Model introduced in allowed operators to type a command and receive a printed response from the computer. The command line interpreter emerged when computers became powerful enough to handle multiple users at once a mode of operation known as time sharing. The Compatible Time Sharing System CTSS developed in at MIT introduced the first true command line interpreter. For the first time a user could type a command such as LOGIN or PRINT and a dedicated program the supervisor would parse that text and execute the corresponding function. In computer scientist Louis Pouzin introduced the software now recognized as a shell for the Multics operating system providing a programmable environment for executing scripts. Many utilities for operating system management and software development provide CLIs. Many CLIs enable software automation since commands can be stored in a script file that can be run repeatedly. A script allows its contained commands to be executed as a group as a single program . Alternatives to a CLI include the following a graphical user interface GUI including the desktop metaphor as in Microsoft Windows text based menus including the DOS Shell file manager and IBM AIX's System Management Interface Tool SMIT keyboard shortcuts Comparison to graphical user interfaces Compared with a graphical user interface a command line interface requires fewer system resources to implement. Since command options can be entered in only a few characters on each command line an experienced user often finds these options easier to access. Automation of repetitive tasks is simplified by line editing and history mechanisms for storing recently or frequently used sequences allowing the review and repetition of commands this capability may extend to a scripting language that can accept parameters and variable options. A command line system may require online or paper manuals for a user's reference although often a help option provides a concise review of the options for a command. The command line environment may not provide graphical enhancements such as the different fonts or extended edit windows found in a GUI. Compared with the icons and drop down menus of a GUI a command line may make it harder for a new user to become familiar with all available commands and options without referring to manuals. Operating system command line interfaces Operating system OS command line interfaces are usually distinct programs supplied with an OS. A program that implements such a text interface is often called a command line interpreter command processor or shell. Examples of command line interpreters include the following Nushell DEC's DIGITAL Command Language DCL in OpenVMS and RSX Unix shells including sh ksh csh tcsh zsh and Bash CP M's CCP DOS' COMMAND.COM as well as the OS and Windows cmd.exe programs the latter groups based heavily on DEC's RSX and RSTS CLIs Under most operating systems the default shell program can be replaced with alternatives examples include DOS for DOS OS for OS and NT Take Command for Windows. The term shell is often used to describe a command line interpreter. Strictly speaking a shell is a command interpreter and processor and by extension a program that provides an interface either a user interface UI command line interface GUI etc. or a programming interface to a command interpreter and processor as well as to the broad capabilities of the operating system. For example the default Windows GUI is a shell GUI named explorer.exe as defined on the SHELL EXPLORER.EXE line in the WIN.INI configuration file. This program strictly speaking is a shell GUI and by extension a shell to be precise the Windows shell is the shell .dll library and explorer.exe is a shell GUI for shell .dll. However explorer.exe is neither a command line interpreter nor a shell CLI. Application programs as opposed to operating systems may also have command line interfaces. An application program may support none some or all of the following three major types of CLI mechanisms Parameters Most command line interfaces support a way to pass additional information to a program when it is launched. Interactive command line sessions After launch a program may provide an operator with an independent means of entering commands. Inter process communication Most operating systems support mechanisms for it for example standard streams or named pipes . Command lines from client processes may be redirected to a CLI program by one of these mechanisms. Some applications support a CLI presenting their own prompt to a user and accepting command lines. Other programs support both a CLI and a GUI. In some cases a GUI is simply a wrapper around a separate CLI executable file. In other cases a program may provide a CLI as an optional alternative to its GUI. CLIs and GUIs often support different functionality. For example all features of MATLAB a computer program for numerical analysis are available via the CLI whereas the MATLAB GUI exposes only a subset. In the video game Colossal Cave Adventure from the player uses a CLI to enter one or two words in order to explore a cave system. History The command line interface evolved from a form of communication used by people via teleprinter or teletype TTY machines. Sometimes these communications involved sending an order or a confirmation using telex. Early computer systems often used a teleprinter to interact with an operator. The mechanical teleprinter was replaced by a glass TTY a keyboard and a screen emulating the teleprinter. Smart terminals permitted additional functions such as cursor movement over the entire screen or local editing of data on the terminal for transmission to a computer. As the microcomputer revolution replaced the traditional time sharing architecture a minicomputer with terminals hardware terminals were replaced by terminal emulators personal computer PC software that interpreted terminal signals sent through the PC's serial ports. These emulators were typically used to interface an organization's new PCs with its existing mini or mainframe computers or to connect one PC to another PC. Some of these PCs ran software for bulletin board systems. Early operating system CLIs were implemented as part of resident monitor programs and these CLIs were difficult to replace. The first implementation of a shell as a replaceable component was part of the Multics time sharing operating system. In Louis Pouzin a staff member of the MIT Computation Center developed the RUNCOM tool for executing command scripts while allowing argument substitution. Pouzin coined the term shell to describe the technique of using commands like a programming language and he wrote a paper on how to implement the idea in the Multics operating system. Pouzin returned to his native France in and the first Multics shell was developed by software engineer Glenda Schroeder. The first Unix shell the V shell was developed by computer scientist Ken Thompson in at Bell Labs and it was modeled on Schroeder's Multics shell. The Bourne shell was introduced in as a replacement for the V shell. Although the Bourne shell is used as an interactive command interpreter it was also intended as a scripting language and contains most features that are commonly seen as producing structured programs. The Bourne shell led to the development of the KornShell ksh the Almquist shell ash and the popular Bourne again shell or Bash . Early microcomputers were based on a command line interface such as CP M DOS or Applesoft BASIC. During the s and s with the introduction of the Apple Macintosh and Microsoft Windows on PCs the command line interface as the primary UI was replaced by the GUI. The command line remained available as an alternative UI often used by system administrators and other advanced users for system administration computer programming and batch processing. In November Microsoft released version . of Windows PowerShell formerly codenamed Monad which combined features of traditional Unix shells with the proprietary object oriented .NET Framework. MinGW and Cygwin are open source packages for Windows that offer a Unix like CLI. Microsoft provides MKS Inc.'s ksh implementation MKS Korn shell for Windows through its Windows Services for UNIX add on. Since the Macintosh operating system macOS has been based on a Unix like operating system called Darwin. On Macintosh computers users can access a Unix like command line interface by running the terminal emulator program called Terminal which is found in the Utilities subfolder of the Applications folder or by remotely logging into the machine using Secure Shell SSH . Z shell is the default shell for macOS Bash tcsh and the KornShell are also provided. Before the version of macOS known as Catalina Bash was the default shell. Usage A CLI is employed whenever a large vocabulary of commands or queries coupled with a wide or arbitrary range of options can be entered more quickly as text than with a pure GUI. This is typically the case with OS command shells. CLIs are also used by systems with insufficient resources to support a GUI. Some computer language systems such as Python Forth LISP Rexx and many dialects of BASIC provide an interactive command line mode generally a read eval print loop environment to allow for rapid evaluation of code. CLIs are often used by programmers and system administrators in engineering and scientific environments and by technically advanced PC users. CLIs are also popular among users with visual disabilities because commands and responses can be displayed using refreshable braille displays. Anatomy of a shell CLI The general pattern of a command line is as follows prompt command param param param paramN prompt output by a program to indicate that it is ready for input a prompt may include contextual information and it often ends with a symbol providing a visual cue that input is expected command input by the user a command is usually one of two types Internal commands are recognized and processed by the command line interpreter. Internal commands are also called built in commands. External commands run separate executables. The command line interpreter searches for executable files that have names matching the external command. param paramN parameters provided by the user. The format and meaning of the parameters depend upon the command. In the case of external commands the values of the parameters are delivered to the program when it is launched by the OS. Parameters may be either arguments or options. In this command line format the delimiters between command line elements are whitespace characters and the end of line delimiter is the newline character. This convention is widely used but not universal. A command line interface can generally be considered to consist of syntax and semantics. The syntax of a CLI is the grammar that all commands must follow. In operating systems DOS and Unix each define their own set of rules that all commands must follow. In embedded systems each vendor such as Nortel Juniper Networks and Cisco Systems defines its own proprietary set of rules. These rules also dictate how a user navigates through the system of commands. The semantics of a CLI define what sort of operations are possible on what sort of data these operations can be performed and how the grammar represents these operations and data in other words the symbolic meaning in the syntax. Two different CLIs may agree on either syntax or semantics however only when these CLIs agree on both can they be considered similar enough that users can work with both CLIs without needing to learn new syntax or semantics and that scripts can be reused. A simple CLI first displays a prompt then accepts a command line typed by the user and terminated by the Enter key and finally executes the specified command and provides a textual display of the results or error messages. Advanced CLIs validate interpret and parameter expand a command line before executing the specified command and they optionally capture or redirect the command's output. Unlike a button or a menu item in a GUI a command line is typically self documenting stating exactly what action the user would like to be performed. In addition command lines usually include many defaults that can be changed to customize results. Useful command lines can be saved by assigning a character string or alias to represent the full command or several commands can be grouped to perform a more complex sequence for example compile a program install it and then run it creating a single entity called a command procedure or script which can be treated as a command. With these advantages a user needs to figure out a complex command or series of commands only once because the commands can be saved for reuse. The commands given to a CLI shell are often in one of the following forms doSomething how toFiles doSomething how sourceFile destinationFile doSomething how inputFile outputFile doSomething how doSomething how doSomething how outputFile In these forms doSomething is in effect a verb how is an adverb for example should the command be executed verbosely or quietly and toFiles is an object or objects typically one or more files on which the command should act. The in the third example is a redirection operator telling the command line interpreter not to send the output of the command to the interpreter's standard output the screen but to the named file instead. This redirection overwrites the target file. Using will redirect the command's output and append it to the target file. Another redirection operator is the vertical bar which creates a pipeline in which the output of one command becomes the input to the next command in sequence. CLI and resource protection On some systems such as Unix like systems or Windows a user can change the set of available commands by modifying which paths appear in the PATH environment variable or its equivalent. On Unix like systems the file containing the executable or script for a command also must be given execute permission. The directories in the PATH variable are searched in the order that they are listed. By reordering the path a user can run for example the executable OS MDOS E.EXE instead of OS E.EXE when the default order is the opposite. Renaming executables also works users often rename their favorite text editor to EDIT for example. A command line allows a person to restrict the available commands for example by blocking access to advanced internal commands. The Bourne shell and workalikes software with similar functionality such as Bash can be run as a restricted shell. Among other effects this restriction prohibits the user from modifying the PATH environment variable so that if PATH is set to include only directories that contain only permitted commands a user can run only those commands. The Windows executable cmd.exe also supports restricting available commands. Often shareware programs limit the range of commands potentially displaying a message at the command line prompt such as Your administrator has disabled running batch files . Some CLIs such as those in network routers have a hierarchy of modes with a different set of commands supported in each mode. Each set of commands is grouped by association with security system interface and so on. In these systems a user might traverse a series of submodes. For example if the CLI has two modes called interface and system the user might use the command interface to enter the interface mode. After entering this mode commands from the system mode may be unavailable until the user exits the interface mode and enters the system mode. In IBM's MVS operating systems the Authorized Program Facility APF allows certain authorized programs to run with enhanced privileges analogous to the superuser account UID in Unix like systems. As another example a set of extensions to IBM's Time Sharing Option environment TSO E supports calling authorized commands but only those commands programs and services in an installation controlled list. A command prompt or prompt is a sequence of one or more characters used in a command line interface to indicate readiness to accept commands. It literally promptss the user to take action. A prompt usually ends with one of the characters or and it often includes other information such as the path of the current working directory and the hostname. On many Unix and derivative systems a prompt commonly ends in a or character if the user is a normal user but a character if the user is a superuser root in Unix terminology . End users can often modify prompts. Depending on the environment these prompts may include colors special characters and other elements. Such elements may be variables and functions for the current time user shell number or working directory. These modifications have several goals for example to make the prompt more informative or visually pleasing to distinguish sessions on various machines or to indicate the current level of nesting of commands. On some systems special tokens in the prompt's definition can be used to cause external programs to be called by the command line interpreter while displaying the prompt. In DOS's COMMAND.COM and Windows NT's cmd.exe users can modify the prompt by issuing a PROMPT command or by directly changing the value of the corresponding PROMPT environment variable. The default prompt of most modern systems the C style is obtained for instance by using PROMPT P G. The default prompt of older DOS systems C is obtained through just PROMPT although on some systems this command produces the newer C style unless used on floppy drives A or B . On those systems PROMPT N G can be used to override the automatic default and explicitly switch to the older style. Many Unix systems feature the PS variable Prompt String although other variables may also affect the prompt depending on the shell used . In the Bash shell a prompt of the form can be set by issuing the command In zsh the RPROMPT variable controls an optional prompt on the right hand side of the display. It is not a real prompt in that the location of text entry does not change. This feature is used to display information on the same line as the real prompt but the information is right justified. In RISC OS the command prompt is a character thus OS CLI commands are often referred to as star commands. A user can also access the same commands from other command lines such as the BBC BASIC command line by preceding a command with a character. In IBM's TSO environment the command prompt is referred to as the READY prompt after the word READY in the prompt. Some shells such as Bash zsh and PowerShell allow the use of prompt systems that display much more information in the command prompt such information may include the type of remote connection the state of machine sensors or additional information about a version control system. These shells often use several ANSI colors Unicode characters and advanced shell features to create a colorful display. A command line argument or parameter is an item of information provided to a program when it is started. A program can have many command line arguments that identify sources or destinations of information or that alter the operation of the program. When a command processor is active a program is typically invoked by typing its name followed by command line arguments if any . For example in Unix and Unix like environments a command line argument might look like this file.s is a command line argument that tells the program rm to remove the file named file.s. Some programming languages such as C C and Java allow a program to interpret the command line arguments by handling them as string parameters in the program's main function. Other languages such as Python expose an OS specific application programming interface API connection between computers or programs through the language's sys module in particular the sys.argv list of command line arguments. In Unix like operating systems a single character used in place of a file name is a special value that specifies that a program should handle data coming from the standard input or send data to the standard output. Command line options A command line option or simply option also known as a flag or switch modifies the operation of a command the effect is determined by the command's program. Options follow the command name on the command line separated by characters such as commas or spaces. Separators are not always required as in the command lines dir and dir in DOS which have the same effect of listing the dir command's available options by contrast the command line dir help in many versions of Unix does actually require the option to be preceded by at least one space and the option is case sensitive . The format of options varies widely between operating systems. In most cases the syntax is by convention rather than being an OS requirement. The entire command line is simply a string passed to a program which can process this string however the programmer would like provided that the interpreter can determine where the command name ends and the command's arguments and options begin. A few representative samples of command line options most related to listing files in a directory illustrate some conventions Command line argument parsing is used to analyze the arguments of a program and such functionality is available in various languages. For example the getopt function for parsing arguments is available in the C POSIX library. In the Multics operating system command line options and subsystem keywords may be abbreviated. This idea appears to derive from the PL I programming language with its shortened keywords e.g. STRG for STRINGRANGE and DCL for DECLARE . For example in the Multics forum subsystem the long subject parameter can be abbreviated as lgsj. In Multics commands are often abbreviated as well typically as the initial letters of words that are connected by underscores to form command names an example is using the abbreviation did for the command delete iacl dir. In some other systems abbreviations are automatic such as accepting enough of the first characters of a command name to identify it uniquely e.g. SU to abbreviate SUPERUSER . Still other systems may have certain abbreviations preprogrammed e.g. MD to abbreviate MKDIR in COMMAND.COM or user defined via batch scripts and aliases e.g. alias md mkdir in tcsh which makes md an abbreviation for mkdir . Option conventions in Unix like systems In Unix like systems an ASCII hyphen minus character begins options the new convention also used by the GNU software collection is to use two hyphens followed by a word e.g. create to identify the option's use. By contrast the old convention still available for frequently used options is to use one hyphen followed by one letter e.g. c . Two hyphen minus characters with no letters may indicate that the remaining arguments should not be treated as options this is useful for example if a file name itself begins with a hyphen or if additional arguments are meant for an inner command e.g. when using the sudo command . Double hyphen minuses are also sometimes used to prefix long options where more descriptive option names are used. This feature is common in GNU software. Although most users think of the shell as an interactive command interpreter it is really a programming language in which each statement runs a command. Because it must satisfy both the interactive and programming aspects of command execution it is a strange language shaped as much by history as by design. The term command line interpreter is applied to computer programs designed to interpret a sequence of lines of text that may be entered by a user or read from a file or other kind of data stream. The context of interpretation is usually that of a given operating system or programming language. Command line interpreters allow users to issue various commands in an efficient and often terse way. This approach requires the user to know the names of commands and their parameters as well as the syntax of the language that is interpreted. The Unix mechanism and the OS EXTPROC command facilitate the passing of batch files to external processors. A user can employ these mechanisms to write specific command processors for dedicated purposes as well as to process external data files that reside in batch files. Many graphical interfaces such as the OS Presentation Manager and early versions of Microsoft Windows use command lines to call helper programs that open documents and programs. These commands are stored in the graphical shell or in files such as the Windows Registry or the OS OS USER.INI file. The earliest computers did not support interactive input output devices often relying instead on sense switches and lights to communicate with a computer operator. This arrangement was adequate for batch systems that ran one program at a time often with the programmer also acting as the operator. This arrangement also had the advantage of low overhead since lights and switches could be tested and set by executing one machine instruction. Later a single system console was added to allow the operator to communicate with the system. From the s onward user interaction with computers was primarily by means of command line interfaces initially on machines such as the Teletype Model ASR and then on early CRT based computer terminals such as DEC's VT . All of these devices were purely text based with no ability to display graphics or pictures. For business application programs text based menus were used however for more general interaction the command line was the interface. Around Louis Pouzin introduced the concept and the name shell in the Multics operating system building on earlier simpler facilities in the Compatible Time Sharing System CTSS . From the early s onward the Unix operating system adapted the concept of a powerful command line environment and introduced the ability to pipe the output of one command as input to another. Unix also had the capability of saving and rerunning strings of commands as shell scripts that behaved like custom commands. The command line was also the main interface for early home computers such as the Commodore PET the Apple II and the BBC Micro almost always in the form of a BASIC interpreter. When more powerful business oriented microcomputers arrived with CP M and then DOS based computers such as the IBM PC the command line began to borrow some of the syntax and features of Unix shells such as globbing and piping output. The command line was first seriously challenged by Xerox PARC's GUI approach used in the Apple Lisa and the Apple Macintosh. A few computer users adopted GUIs such as GEOS and Windows . but the majority of IBM PC users did not replace their COMMAND.COM shell with a GUI until Windows was released in . Scripting Most command line interpreters support scripting to various extents. After all they are interpreters of an interpreted programming language though in many cases the language is unique to the particular command line interpreter. These interpreters handle scripts variously termed shell scripts or batch files written in the language that they interpret. Some command line interpreters also incorporate the interpreter engines of other languages such as Rexx in addition to their own language thereby allowing scripts in those languages to be executed directly within the command line interpreter itself. Conversely scripting programming languages in particular those including an eval function such as Rexx Perl Python Ruby or Jython can be used to implement command line interpreters and filters. For a few operating systems most notably DOS such a command interpreter provides a more flexible command line interface than the one supplied. In other cases such a command interpreter can present a highly customized UI using the user interface and input output facilities of the language. Other command line interfaces The command line provides an interface between programs as well as between programs and users. In this sense a command line is an alternative to a dialog box. Editors and databases present a command line in which alternative command processors might run. On the other hand a user might have options on a command line which opens a dialog box. It is typically used by game developers during development and by mod game modification developers for debugging purposes as well as for cheating or skipping parts of the game.
